# foundry-repo-hygiene

Covers two things that are easy to get backwards or let slide silently: how a repo's *first* commit should be sequenced, and the ongoing discipline of keeping documentation honest as code changes — neither of which is really a "security" concern or a "docs template" concern on its own.

**`EXPLAIN_MODE`** (set by `foundry-init`, or ask if standalone): in `detailed` mode, explain the sequencing rationale before applying it — `.gitignore` goes in before the first `git add`, not after, because once a secret is committed it's in history even if later deleted; fixing the order in advance is strictly cheaper than cleaning up after the fact. In `brief` mode, just apply the sequence.

## Part 1 — new repo sequencing (use during initial setup)

**`foundry-init` invokes this skill twice — once for Part 1 (Step 2.1, new-repo sequencing) and once for Part 2 (Step 2.7, ongoing-docs discipline).** Each invocation runs only its own Part, not both — Part 1 is unambiguously setup-only (first-commit sequencing) and Part 2 is unambiguously ongoing discipline (the `{{ADDITIONAL_RULES}}` addition and the standalone freshness check), so there's no overlap to accidentally re-run. Noted explicitly here (Session 19, cosmetic finding) since this file is the same target both times and previously had no internal marker saying so — the boundary lived only in `foundry-init`'s own prose about this skill.

The common mistake this prevents: writing code first, committing it, *then* adding `.gitignore` and security rules — by which point a secret may already be in history (see `foundry-security` step 3 for what to do if that's already happened).

**Check first whether this is even a git repo yet** (`git rev-parse --is-inside-work-tree` or equivalent). If not, and the project is meant to be version-controlled, `git init` is step 1 below, not assumed already done. If the user has deliberately chosen not to use git for this project, skip the git-specific steps below entirely (the doc/hook scaffolding still applies fine without git) rather than forcing a `git init` they didn't ask for.

**Correct order for a brand-new project:**
1. `git init`
2. Write/merge `.gitignore` — **before the first `git add`**, not after. This step always writes *something*, regardless of `HANDLES_SECRETS`: a seventh fresh-eyes review (Session 19) found that a non-secrets project previously got no `.gitignore` at all, because the only writer was `foundry-security`'s secrets-pattern baseline, gated entirely on `HANDLES_SECRETS=true`. A project with no credentials still has OS/build junk that shouldn't enter history (`.DS_Store`, `__pycache__/`, `node_modules/`, `.venv/`, `dist/`/`build/`, language-appropriate equivalents — infer from the stack named in Step 1's questionnaire). Write this universal baseline here, unconditionally, before the first commit. Then, **only if the project handles secrets**, hand off to `foundry-security`'s `.gitignore` step to merge the credential-pattern baseline on top (merge, never replace what was just written — same discipline as everywhere else). This makes `.gitignore` itself, not just its secrets-pattern subset, a universal first-commit concern.
3. Run `foundry-docs` to create CLAUDE.md/DECISIONS.md/SESSIONS.md.
4. Run `foundry-hooks` to wire the SessionStart loader (and secrets-guard, if applicable).
5. Only then write/add actual project code.
6. First commit should include the scaffolding (docs, `.gitignore`, `.claude/settings.json`) as one coherent commit — not mixed in ad hoc with the first feature code, so the scaffolding is easy to find/reference later (`git log` shows "project scaffolding" as a distinct, identifiable point in history).
7. Before any commit at any point: confirm working tree status and diff, never blind-stage with `git add -A`/`git add .` — stage specific files, consistent with standing git-safety practice.

**For an existing repo being retrofitted** (Foundry added after the fact): don't try to rewrite history to "fix" the sequencing — that's a destructive operation with low payoff. Just apply `foundry-security`'s already-committed-secrets check (step 3 in that skill) to see if anything needs rotating, then proceed with the scaffolding as a normal new commit going forward.

## Part 2 — keeping documentation honest over time (an ongoing discipline, not a one-time setup step)

This isn't something a hook can fully enforce (a hook can't judge whether a README *description* is still accurate), but Foundry should make the expectation explicit and give the user/assistant a concrete check to run periodically, rather than leaving "keep docs current" as a vague aspiration.

**What gets added to the generated CLAUDE.md's Rules section** (coordinate with `foundry-docs` — this is additional content for `{{ADDITIONAL_RULES}}` when this skill runs):
- "Update SESSIONS.md and, if status changed, CLAUDE.md as part of the same work — not as a separate cleanup pass remembered later. A session that changed behavior but didn't update these docs is not finished."
- "If README.md describes a feature, command, or setup step that no longer matches reality, fix the README in the same change — don't leave it to drift."

**README changelog/roadmap discipline (`foundry.readmeChangelogDiscipline`; recommended default is `on` once asked — see below).** Distinct from the rule above: the rule above catches README *describing something wrong* (a stale setup step, a removed feature still documented). This catches a different failure — a README with a Roadmap/changelog-style checklist (`- [x] ~~done item~~`, `- [ ] planned item`) silently falling behind real fixes that landed in other docs (CLAUDE.md/SESSIONS.md) but never got a corresponding README entry. The two docs drift apart even though neither is individually "wrong" yet.

Don't ask this at `foundry-init` time — there's no README content yet to reason about, and the user has no real basis to judge whether they want the discipline. Instead: **the first time a push would update CLAUDE.md/SESSIONS.md without a corresponding README change, and `foundry.readmeChangelogDiscipline` is unset**, ask once: "This project's README has a Roadmap/changelog-style section. Want every push that changes tracked status to also update README in the same commit (recommended — keeps it from quietly falling behind, as CLAUDE.md/SESSIONS.md already discipline themselves to do), or treat README as a periodic catch-up instead?" Record the answer as `foundry.readmeChangelogDiscipline: "on"` or `"off"` in `.claude/settings.json` (merge, same discipline as every other settings write in Foundry) so it's asked once per project, not every push. **If the project's README has no Roadmap/changelog-style section yet, don't leave the field untouched** — write `foundry.readmeChangelogDiscipline: "not-applicable-yet"` instead. An eighth fresh-eyes review (post-Session-19 follow-up) found that leaving the field genuinely unset on skip makes "skipped, correctly, because no section exists" indistinguishable from "never reached this check" — if the project later grows a Roadmap section, nothing re-triggers the one-time question, and the discipline silently never engages unless `foundry-repo-hygiene` happens to be invoked standalone again. Recording the explicit `"not-applicable-yet"` state means a later check (the standalone freshness check below, or the next time this question's trigger condition fires) can detect the transition and actually ask: if `foundry.readmeChangelogDiscipline == "not-applicable-yet"` and README now has a Roadmap/changelog section, treat it as unset and ask the question for real.

Once set to `"on"`: every commit that updates CLAUDE.md's Current Status or adds a SESSIONS.md entry should be checked against README's Roadmap/changelog section in the same change — if the fix/feature warrants a corresponding entry there, add it before committing, not as a later catch-up pass. If `"off"`, the standalone freshness check below (item 1) is the only mechanism that resurfaces README staleness, and that's a deliberate, recorded choice, not an oversight.

**Auto-load budget discipline (`foundry.docBudgetDiscipline`; recommended default is `on` once asked — see below).** Distinct again from both rules above: those catch a document being *wrong*. This catches a document set being *too expensive* — the auto-loaded docs (CLAUDE.md, plus whatever the SessionStart doc-loader hook cats in) growing until they consume a large fraction of every session's context window before the user types anything. Nothing about the files is incorrect when this happens, which is exactly why nothing catches it: Foundry's own repo grew its auto-loaded set from 16,874 bytes to 303,867 (~76,000 tokens, ~38% of a 200k window) across ~20 sessions, and every doc check stayed green the whole way up, because every individual session's addition was small and reasonable. The fix each time is cheap (move old material to an archive file, verbatim, leave a pointer); noticing is the hard part.

`foundry-audit`'s auto-load budget check is the noticing mechanism — it reports the injected total, per-file breakdown, and percentage of budget on every run, INFO once over budget, FAIL at a hard ceiling. **This entry is the other half: what the project does when that line goes over.** The check can only report; it cannot decide whether this project wants an archive pass scheduled as due work.

Don't ask this at `foundry-init` time — same reasoning as the README discipline above, and more so: at init the doc set is a few KB of template and the question is unanswerable. Instead: **the first time `foundry-audit`'s auto-load budget check reports INFO or FAIL in this project, and `foundry.docBudgetDiscipline` is unset or `"not-applicable-yet"`**, ask once: "This project's auto-loaded docs have crossed their size budget (`foundry-audit` reports the total and which file is largest). Want an archive pass treated as due work — when the budget line is over, the session archives the largest contributor verbatim to a `*_ARCHIVE.md` and leaves a pointer, in the same change (recommended) — or treat the budget line as advisory and catch up periodically?" Record `foundry.docBudgetDiscipline: "on"` or `"off"` in `.claude/settings.json` (merge, same discipline as every other settings write in Foundry).

The INFO tier is deliberately set with runway rather than at the point of pain, so asking here is not asking too late: the threshold is chosen to fire roughly five average sessions' worth of growth before the hard ceiling. There is no second, earlier "getting close" trigger and no second threshold to defend — the headroom in the first one is what buys the time to answer.

Once set to `"on"`: any session that adds to the auto-loaded docs runs `foundry-audit` before pushing and, if the budget line is over, does the archive move in the same change — verbatim, never summarised during a move, with a pointer to the archive left in the auto-loaded file (an archive nothing points to is indistinguishable from a deleted one). Add the matching bullet to the generated CLAUDE.md's Rules section via `{{ADDITIONAL_RULES}}` at that point — not before, since an unconditional rule about a threshold this project may never reach is noise in the file whose size is the thing being protected.

**The negative branches, written out by name — because every one of them has a silent-default failure mode and this repo has shipped that exact shape before:**

1. **The budget check never fires in this project's lifetime.** The likely case: most projects' docs never reach the threshold. The question is then never triggered, and the field stays unset — indistinguishable from "this check was never reached", which is the precise defect the `"not-applicable-yet"` state on `foundry.readmeChangelogDiscipline` exists to fix. Same fix here: the **first time the standalone freshness check below runs the budget check and finds the set comfortably under budget, write `foundry.docBudgetDiscipline: "not-applicable-yet"`.** That records "measured, genuinely not relevant yet" rather than silence, and gives item 8 below something to detect a transition against.

2. **The check fires before the setting has ever been asked.** This is the *normal* first occurrence, not an anomaly — and it must not be read as "no discipline is configured, so carry on". **Unset, or `"not-applicable-yet"`, when the budget is over, means ask now and do the archive pass within this session's scope.** It never means `"off"`. Absence of an `"on"` is absence of an answer, not a recorded decision to skip; treating the two as the same is the failure this repo has found in eight consecutive review rounds.

3. **`"off"` was chosen.** Then nothing schedules an archive pass, and the audit's own INFO line is the only surface that resurfaces it — a deliberate, recorded choice, not an oversight, and worth saying out loud at the time so it isn't rediscovered later as a gap. Note what `"off"` does *not* do: the hard-ceiling FAIL still fails the audit, because `"off"` is a preference about when the work gets scheduled, not permission to disable a mechanical check.

4. **`foundry-audit` is never run in this project.** Then nothing measures the budget at all, every branch above is unreachable, and the field stays unset with no mechanism able to fill it. This is a real limit and not covered by anything else in Foundry — the discipline is only as live as the audit runs are. Say so rather than assuming the audit gets run: the practical mitigation is `foundry-audit`'s own advice to run it before a push that changed documentation, and if this project never does that, treat the whole budget mechanism as not installed rather than as passing.

**Verification status: none, and that is not a gap being hidden.** Everything in this entry is prose judgment for a future session to follow — there is no artifact to inject a defect into, so no case in `tests/run_fixtures.sh` covers it and none can. The *measuring* half (`foundry-audit`'s budget check, its thresholds, its INFO/FAIL split, and the loaded-set derivation it reads from `.claude/settings.json`) is mechanical and mutation-tested. The *deciding* half is this file, and a green fixture suite says nothing whatsoever about it.

**A standalone freshness check** (`foundry-repo-hygiene` can run this on request, e.g. "audit doc freshness"):
1. Check `git log -1 --format=%ci -- README.md` vs. `git log -1 --format=%ci` (most recent commit overall) — if the gap is large relative to the project's commit cadence, flag it as a candidate for review (not an automatic failure — a stable README that hasn't needed changes isn't necessarily stale).
2. Read README.md's stated "how to run" / setup commands and actually try them (or at minimum check the referenced files/scripts still exist) — a command that references a deleted file is a concrete, checkable staleness signal, not a guess.
3. Check whether CLAUDE.md's "Current status" section references things (files, agents, features) that still exist in the codebase — grep for the named files/symbols.
4. **If CLAUDE.md has a REGULATORY CONTEXT or COMPLIANCE/AUDIT TRAIL section** (written by `foundry-governance`), explicitly include it in this check — regulatory guidance changes over time and that section is dated for exactly this reason, but nothing else in Foundry ever resurfaces it for review. Check the date stated in that section against today; if it's been more than a few months (use judgment based on how fast-moving the relevant regulatory area is — ask the user if unsure), flag it specifically as "this compliance section was written on X and may be stale — worth re-verifying with the relevant regulatory source before continuing to rely on it," not just lumped in with general doc staleness.
5. **If the project was originally scaffolded via the minimal/throwaway fast-path** (check `foundry.scaffoldMode` in `.claude/settings.json`, if present) but now has real complexity (handles secrets, has grown significantly, etc.), flag this explicitly: "this project was scaffolded as a quick/minimal setup — if it's become a real project now, consider re-running `/foundry-init` for the full questionnaire (security baseline, etc.)." This is the only mechanism that catches a throwaway script that quietly became a real project with no security baseline.
6. **If `foundry.readmeChangelogDiscipline == "not-applicable-yet"`** (see above) and README.md now has a Roadmap/changelog-style section, the project has crossed the same kind of state transition as item 5 — re-ask the discipline question now, since it was correctly skipped at the time but the precondition has since changed.
7. **Run `foundry-audit`'s auto-load budget check** (`bash ~/.claude/skills/foundry-audit/audit.sh`, the `auto-load budget` line) and handle `foundry.docBudgetDiscipline` from what it says — this is the item that keeps the discipline above from depending on someone happening to run an audit at the right moment. If the line is under budget and the field is unset, write `"not-applicable-yet"` (negative branch 1). If it reports INFO or FAIL and the field is unset **or** `"not-applicable-yet"`, the project has crossed the same kind of state transition as items 5 and 6 — ask the one-time question for real now (negative branch 2). If the line is SKIP, the injected size could not be measured at all: report that as unknown, not as fine, and do not write the field.
8. Report findings plainly; don't auto-fix without showing the user what's stale and why first.

## Closing out

Whichever Part ran, end the turn with an `AskUserQuestion` offering the real next steps rather than a prose summary the user has to respond to freehand. Part 1's usual options: stage the scaffolding files for the first commit (staged, reviewed, *not* committed — see below), proceed to writing actual project code, or run `foundry-security`'s already-committed-secrets check on a retrofitted repo. Part 2's usual options: run the standalone freshness check now, fix a specific staleness finding it surfaced, or record the `foundry.readmeChangelogDiscipline` answer and move on. 2-4 options; "Other" is built in.

Never phrase an option in a way that reads as pre-authorization to commit — "commit only when explicitly asked" is a standing rule this skill writes into the project's own docs, so the option is "stage and show the diff," and the commit itself needs its own explicit ask. Equally, this convention is not a reason to ask about things with obvious answers: `.gitignore` goes in before the first `git add` because the sequencing is already decided (Part 1, step 2), so that just happens — the standing "pick the sensible default and proceed" guidance still applies inside the flow.

Each Part has one conditional addition. In Part 1, on a repo being retrofitted rather than created, list `/qc-review` next to the already-committed-secrets check. No further threshold applies: the retrofit branch at Part 1's opening already means a repo with commits, and one commit can carry a credential as easily as three hundred. An earlier draft added "history long enough to have leaked something," which sounds like a filter and excludes nothing the enclosing branch hadn't already excluded.

Part 2's is trickier, and the honest resolution is to offer it as *part of the fix option itself* rather than as a separate gated entry. Item 7 reports staleness without fixing it, so at the close of the freshness pass nothing has been corrected yet and a "corrections were made" trigger is false — while the turn where corrections do land is a later one this section no longer governs. Writing the trigger for that later turn just relocates it out of scope. So: when the closing question offers to fix a staleness finding, say that `/foundry-audit` is the check worth running once the edits land, and let the user take both in one choice. If they read the report and move on without fixing anything, nothing was edited and nothing needs auditing — that is the negative branch, and it is silence for a stated reason rather than by omission.
