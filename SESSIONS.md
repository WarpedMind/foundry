## 2026-10-25 (`.dev.vars` folded into the secrets baseline)

Side session off yesterday's Hook 2 work, doing the first of its follow-ups: Cloudflare's `.dev.vars` was in **none** of Foundry's baselines, while `learnello` and `growfamilycloud` had each independently added it to their own copy of Hook 2's regex. Deliberately done *before* those two projects are re-synced to the template, so the swap cannot delete what they are relying on; they can now drop their local alternatives. Decision and the form rationale: DECISIONS.md, today.

**Fixture cases first, and the suite was watched going red before anything was changed** — the repo's standing order for this pattern, and it paid: all six new catch-cases failed against the unmodified baselines, which is what makes them discriminating rather than decorative. Then four separate neuter-tests after the fix, because a drift guard that fires is not the same as end-to-end coverage: dropping the alternative from the **template only** (drift guard fires *and* the block-reason case fires independently); from **`SG_REGEX` only** (regex cases plus the drift guard); dropping `.dev.vars.example` from the template's **exclusion** only (the new exclusion drift guard plus the clean-index exit-0 case); and swapping **both** copies to `learnello`'s `(\..*)?$` form (the `allow .dev.vars.d/README.md` case, which is the only thing pinning the component-anchored form). One of these first passed for the wrong reason — a `perl` quoting bug made the mutation a no-op, so the suite stayed green having tested nothing — caught only because the mutated line was printed and read. Same lesson as yesterday's escaping bug in the drift-guard neuter-test, one day later.

**Added beyond the brief:** a drift guard for the `grep -vE` exclusion, which had none. The suite asserted the template carried the tested *regex* verbatim but said nothing about the exclusion beside it — the one thing keeping `.env.example` committable — so the template could have lost its allowlist with the regex section still green off its own local copy. Exactly the shape of defect yesterday spent the day on. The template was regenerated with the documented `jq -n --rawfile` recipe rather than hand-edited, and the extracted command confirmed byte-identical through the JSON round-trip; the first comparison reported a mismatch that turned out to be a bug in the comparison pipeline, not the file.

**Then the duplicate-baseline gap, noticed while editing both copies by hand, was fixed too.** The `.gitignore` baseline existed twice — the prose list in `foundry-security/SKILL.md` step 1 and a heredoc in `tests/run_fixtures.sh` — with nothing asserting they agreed: the same structure as the `exit 1` secrets-guard, a suite exercising its own transcription while the artifact projects receive drifts freely. Fixed by deleting the copy rather than guarding it: the suite now extracts the fenced block from the skill, anchored on step 1's heading, and fails with a message naming that file if the extraction breaks. The deleted heredoc and the extracted block were confirmed byte-identical first (the first comparison attempt grabbed every heredoc in the file, because a `sed` range re-triggers — the second found them identical). A drift guard was the other option and was deliberately not taken: two copies need a *reason* to exist, as they do for the hook's regex, where the shipped artifact is generated JSON and the test needs a plain string. Nothing forces two here, and deleting one removes the failure mode where guarding it only detects it. Note the direction is opposite to Hook 2's fix — prose out, template in — because what a project receives differs: Hook 2 ships a byte-exact command, while the baseline is merged into whatever `.gitignore` already exists and extended per project, so the fenced block *is* the artifact.
