## 2026-10-24 (Secrets-guard made to actually block — and the validation habit that let it ship)

Ran `PROPOSALS/2026-10-24-secrets-guard-exit-code-handoff.md`, all six items. Re-verified the diagnosis against the live hook contract first rather than trusting the handoff: on `PreToolUse`, `exit 2` blocks and stderr carries the reason; `exit 1` with no JSON is a *non-blocking* error and plain stdout is never surfaced for that event. So the guard neither blocked nor spoke, exactly as reported.

**Two things the handoff did not know, both found by scanning `~/Projects` before writing any code.** First, only **one** project was actually broken. Seven carry the hook; three had been hand-repaired to `exit 2` + stderr, three to a JSON `deny`, and only `karbotrage/karbotrage_v1` still had `exit 1`. Six sessions, six independent improvisations, not one of which corrected the skill they came from — which reframed the fix: the exit code was the symptom, a retyped-per-project snippet with no single point of correction was the mechanism. Second, **the root cause is written down in this repo as proof of correctness.** `SESSIONS_ARCHIVE.md`'s Session 6 entry records a real `git add -f .env` "to confirm the secrets-guard `PreToolUse` hook genuinely blocks it (exit 1)". That session ran the script, saw non-zero, and wrote it down as blocking. Accurate observation, wrong inference, never revisited — because every later check re-tested the regex instead.

**Fixed.** `exit 2` with the reason on stderr, chosen over a JSON `deny` on failure direction: a mistyped `permissionDecision` fails *open*, which is the defect being fixed, while an exit code either is 2 or isn't. Hook 2 got the template file it never had (`templates/settings.secretsguard.json.template`), the prose now shows the bare regex instead of runnable snippets ending in `exit 1`, and the command self-scopes on `.tool_input.command` rather than relying only on the best-effort `if` field — which matters *because* it now blocks, since an unscoped version would deny every Bash call while a credential sat in the index, including the `git restore` needed to escape.

**The fixture case now asserts blocking, not classification.** The old suite tested whether the regex classified filenames and had never executed the hook, so the exit code was never in its field of view. New section extracts the command from the template and asserts exit 2, the reason on stderr, and that non-commit commands pass untouched. Three mutation-case probes: restore `exit 1`, drop the `>&2`, strip the scoping — each confirmed to turn the matching assertion red, and each then neuter-tested in the other direction (made into a no-op, confirmed the case reports "mutation not caught"). A template-regex drift guard was added and also neuter-tested; the first attempt at that test passed for the wrong reason — a backslash-escaping bug made the mutation a no-op — which is itself the argument for neuter-testing rather than trusting a red/green.

**Asking item 4's question of every other hook found a second defect.** Hook 5's push advisory was emitting `permissionDecision: "allow"` beside its `systemMessage`, justified in its own SKILL.md as "redundant (PreToolUse defaults to allow), but explicit." Not redundant — `"allow"` skips the permission prompt, so the hook warning that a push looked risky was removing the confirmation for that push. Strictly less safe than silence, same root cause as Hook 2, opposite direction. Fixed to `systemMessage` only, with a fixture case asserting no permission decision ever comes back. Hook 1/3's `additionalContext` and Hook 4's log write were checked against the docs and are correct.

**Items 5 and 6.** `foundry-audit`'s reference check got the archive-aware tier, resolving citations into `DECISIONS_ARCHIVE*.md` as a second tier, plus the content-only fix for the filename-prefix bug; both allowlist entries from this morning deleted (`2026-06-30` stays — it resolves nowhere and never did). Worth stating plainly: the archive tier changes real output, the narrowing changes **nothing** on this doc set (both extractions yield the identical four dates, checked directly), so its only evidence is its mutation case. Mutation cases 51 → 54. SESSIONS.md's own archive pass done, verified by reconstructing the original from its two halves and `cmp`-ing byte-for-byte; the budget fell 68% → 62%, and this session's own write-up returned it to **just over 70%** (each correction to this very paragraph nudged it again, which is exactly why the rule is to read the figure from `audit.sh` and never to copy it into prose) — the cost this morning's entry predicted, measured after writing rather than before, landing exactly on the "~70% or below" line. `DECISIONS.md` is now the largest contributor at 40.3KB, so it is next in line.

**One defect the fixtures could not have found, caught by the end-to-end run.** The block message told the user to unstage with `git restore --staged <file>`. That command fails outright in a repo with no commits — `fatal: could not resolve HEAD` — and the first commit is precisely when this guard most often fires, since `foundry-repo-hygiene`'s whole first-commit sequencing exists for that moment. So the remedy was wrong in the single likeliest case. Now `git rm --cached <file>`, which works with or without a HEAD and leaves the file on disk; both unstage commands have fixture cases, because a guard that blocks its own escape hatch traps the user. Worth noting how it surfaced: every assertion in the suite passed before and after, because they check the exit code and that the message names the file, not whether the advice in it is executable. Wiring the real template into a scratch project and actually following its instructions is what found it.

**Also done:** `karbotrage_v1` rewired to the tested artifact and confirmed blocking *in that repo* via a throwaway `GIT_INDEX_FILE`, so nothing in the user's working tree or index was touched. USER_GUIDE.md now carries the one-line check (`grep -o 'exit [0-9]' .claude/settings.json`) and the fix for projects scaffolded before today, and `foundry-hooks` gained a step telling a standalone invocation not to assume an existing Hook 2 is current.
