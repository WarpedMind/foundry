## 2026-10-24 (Secrets-guard made to actually block — and the validation habit that let it ship)

Ran `PROPOSALS/2026-10-24-secrets-guard-exit-code-handoff.md`, all six items. Re-verified the diagnosis against the live hook contract first rather than trusting the handoff: on `PreToolUse`, `exit 2` blocks and stderr carries the reason; `exit 1` with no JSON is a *non-blocking* error and plain stdout is never surfaced for that event. **Two things the handoff did not know, both found by scanning `~/Projects` before writing any code.** First, only **one** project was actually broken. Six sessions, six independent improvisations, not one of which corrected the skill they came from — which reframed the fix: the exit code was the symptom, a retyped-per-project snippet with no single point of correction was the mechanism. Second, **the root cause is written down in this repo as proof of correctness.** `SESSIONS_ARCHIVE.md`'s Session 6 entry records a real `git add -f .env` "to confirm the secrets-guard `PreToolUse` hook genuinely blocks it (exit 1)". That session ran the script, saw non-zero, and wrote it down as blocking. Accurate observation, wrong inference, never revisited — because every later check re-tested the regex instead.

**Fixed.** `exit 2` with the reason on stderr, chosen over a JSON `deny` on failure direction: a mistyped `permissionDecision` fails *open*, which is the defect being fixed, while an exit code either is 2 or isn't. Hook 2 got the template file it never had (`templates/settings.secretsguard.json.template`), the prose now shows the bare regex instead of runnable snippets ending in `exit 1`, and the command self-scopes on `.tool_input.command` rather than relying only on the best-effort `if` field — which matters *because* it now blocks, since an unscoped version would deny every Bash call while a credential sat in the index, including the `git restore` needed to escape.

**The fixture case now asserts blocking, not classification.** The old suite tested whether the regex classified filenames and had never executed the hook, so the exit code was never in its field of view. New section extracts the command from the template and asserts exit 2, the reason on stderr, and that non-commit commands pass untouched. Three mutation-case probes: restore `exit 1`, drop the `>&2`, strip the scoping — each confirmed to turn the matching assertion red, and each then neuter-tested in the other direction (made into a no-op, confirmed the case reports "mutation not caught"). A template-regex drift guard was added and also neuter-tested; the first attempt at that test passed for the wrong reason — a backslash-escaping bug made the mutation a no-op — which is itself the argument for neuter-testing rather than trusting a red/green.
