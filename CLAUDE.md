# Foundry

## What this is
Foundry scaffolds software projects with the documentation structure, hooks, and guardrails that make AI-assisted development reliable across many sessions, derived from a short per-project questionnaire rather than a fixed template. Part of the "Preamble" brand (Preamble = the umbrella; Foundry = this specific tool; Promptify = a separate, related tool also living here for now).

## Stack
- Claude Code skills (Markdown `SKILL.md` files, no compiled code)
- Bash (`install.sh`, hook commands)
- `jq` for hook JSON generation/validation

## Architecture
- `skills/foundry-init/` — orchestrator; calls the others in sequence based on a questionnaire; writes the `foundry.scaffolded`/`scaffoldedDate` marker into `.claude/settings.json` on successful completion, and `foundry.dismissed` if the user declines the status hook's offer
- `skills/foundry-docs/` — renders `templates/*.template` into a project's CLAUDE.md/DECISIONS.md/SESSIONS.md
- `skills/foundry-hooks/` — wires hooks into a project's `.claude/settings.json`: Hook 1 (SessionStart doc-loader), Hook 2 (secrets-guard pre-commit, only if `HANDLES_SECRETS`), Hook 3 (status/offer — checks `foundry.scaffolded`/`foundry.dismissed`, always added), Hook 4 (directory-drift logger — optional, `PreToolUse`/`Bash`, logs out-of-project `cd`s to `.claude/drift.log`), Hook 5 (push-time `qc-review` offer — optional, `PreToolUse`/`Bash` matching `git push`, fires a one-time-per-session `systemMessage` advisory when the pushed commits touch `qc-review`'s own risk-path keywords; never blocks, never auto-runs the review; distinct from the `PostToolUse` auto-run rejected 2026-06-28 — see `DECISIONS_ARCHIVE.md`)
- `skills/foundry-security/` — `.gitignore` baseline, `.env.example` convention, already-committed-secrets check
- `skills/foundry-repo-hygiene/` — new-repo commit sequencing, ongoing docs-freshness discipline; Part 2 also owns the two one-time settings-recorded disciplines (`foundry.readmeChangelogDiscipline`, `foundry.docBudgetDiscipline`), both asked when the check first becomes relevant rather than at init time, both with an explicit `"not-applicable-yet"` state so a skip is distinguishable from never having been reached
- `skills/foundry-governance/` — regulatory/compliance section content, with an explicit anti-fabrication rule (states "not yet researched" rather than inventing plausible compliance language)
- `skills/foundry-stack/` — STACK.md setup/maintenance for career/portfolio documentation (separate audience/lifecycle from the other docs); enforces a "why this over alternatives" rule on every non-trivial entry, not just "what was used"
- `skills/promptify/` — standalone; `/promptify` and `/promptify!`, not dependent on the rest of Foundry
- `skills/foundry-help/` — standalone; on-demand `/foundry-help` explainer of what Foundry is and which skill to reach for. Deliberately not an automatic session-start banner: Hook 3 already owns that slot (three-state design exists specifically to avoid nagging, `DECISIONS_ARCHIVE.md` 2026-06-28), and the VSCode extension doesn't render a SessionStart hook's `additionalContext` as visible text at all (Session 20), so a banner would be invisible exactly where a new user most needs it. An on-demand command renders as a normal response on every platform instead.
- `skills/foundry-audit/` — standalone; mechanical structural audit of a project's doc set (dangling decision references, decision-log ordering, broken/stale file paths, unreachable docs, unclosed fences, `Enforced at:` targets that don't exist, and the auto-load budget — the byte size of the document set the SessionStart hook injects into every session, INFO over 160,000 B and FAIL at a 304,000 B ceiling, measured against the loaded set parsed out of `.claude/settings.json` rather than a hardcoded three filenames). The only skill here whose logic lives in a real script (`skills/foundry-audit/audit.sh`) rather than in `SKILL.md` prose, and deliberately so: prose can't be mutation-tested, and every FAIL-capable check has an injected-defect case in `tests/run_fixtures.sh`. Checks that genuinely need semantic judgment are kept *out* of the script and labeled as judgment in `SKILL.md` so they can't borrow the tested checks' credibility. Referenced-not-owned, same footing as `qc-review`/`promptify`
- `skills/oneshot/` — standalone; batches every clarifying question a task needs into one `AskUserQuestion` call instead of asking one at a time, plus a symmetric closing-out convention (offer next steps as options, not open prose). Not project-scaffolding-specific — same "standalone, works anywhere" placement as `promptify`
- `templates/` — the actual template files the above skills render (`templates/CLAUDE.md.template`, `templates/DECISIONS.md.template`, `templates/SESSIONS.md.template`, `templates/STACK.md.template`, `templates/settings.hooks.json.template` [doc-loader], `templates/settings.status.json.template` [status/offer], `templates/settings.qcreview-offer.json.template` [Hook 5 push-time qc-review offer])
- `install.sh` — symlinks `skills/*` into `~/.claude/skills/`
- `tests/run_fixtures.sh` + `tests/fixtures/*.txt` — committed, re-runnable adversarial fixture suite for the `.gitignore` baseline and secrets-guard regex (previously one-time manual checks only); also runs Hook 4's (directory-drift logger), Hook 3's (status/offer), Hook 5's (push-time qc-review offer), the Hook 1/3 SessionStart-merge-guard, and `foundry-audit`'s 38 mutation cases inline in the same script, since none of these fit the `*.txt` file's static-filename-match shape — run automatically via `.github/workflows/fixtures.yml` on every push/PR. The `foundry-audit` suite is the odd one out structurally: the others assert a pattern classifies an input correctly, while that one builds a whole synthetic project tree, confirms it audits clean, then injects one known defect per check class to prove each check can actually fail
- `tests/calibration/qc-review/` — a committed calibration fixture for `qc-review`: a subject file with five planted defects (one per failure class its Step 2 commits to hunting), an answer key with per-defect grading rules, a procedure, and an append-only results log. Deliberately **not** run by `tests/run_fixtures.sh` and never a CI gate — the review dispatches a non-deterministic, billed LLM subagent that cannot run in GitHub Actions. Manual periodic calibration, graded for partial credit rather than pass/fail; the suite prints an explicit NOT COVERED line so the omission is visible rather than silent
- `CONTRIBUTING.md` — dev setup, fixture-suite usage, and PR expectations for external contributors

## Where the history lives

Older material is archived out of this file to keep the SessionStart auto-load small. It is
**not** loaded into sessions and should not be opened unless the task genuinely needs it
(see the archive rule under Rules / Never do).

- `PROJECT_HISTORY.md` — the full per-session narrative log formerly in `Current status`,
  Sessions 4-20 (2026-06-28 → 2026-08-18). Open it to reconstruct how a mechanism reached
  its current shape, or what an earlier review round actually found.
- `SESSIONS_ARCHIVE.md` — session entries older than the newest two. Open it when tracing
  when and why something changed.
- `DECISIONS_ARCHIVE.md` — decision entries from 2026-06. Open it when a current rule looks
  arbitrary and you need the reasoning that produced it, or to check whether an approach was
  already tried and rejected.

Everything here is also in git history; these files exist so it is findable without knowing
to go looking.

- **The doc-budget mechanism is built and mutation-tested, but has never fired outside a fixture — no real project has yet crossed the threshold.** Item 4 shipped 2026-08-18: `foundry-audit`'s auto-load budget check (INFO at 160,000 B, FAIL at a 304,000 B ceiling, thresholds derived two independent ways — see its SKILL.md) plus `foundry.docBudgetDiscipline` in `foundry-repo-hygiene` Part 2. This closes the "one-time cut, not a durable fix" item: growth back to the pre-cut size now gets caught rather than repeating silently. What remains open is narrower and worth not overstating. (1) This repo sits at ~60% of budget, so the INFO tier has fired only against injected fixtures, never on real prose — the same designed-but-never-fired-for-real status as `foundry-repo-hygiene`'s staleness checks below. (2) The threshold's *lead-time* half is a prediction: ~76,000 B of headroom ≈ five average sessions, derived from this repo's measured history, but whether five sessions is actually enough warning in practice is unmeasured until it trips. If it fires and the archive pass feels rushed, that is evidence to lower the number, not to raise it. (3) The discipline half is prose with no mechanical surface, and its branch 4 (a project that never runs `foundry-audit` at all) has no mechanism behind it by construction — written out in that file rather than papered over.
- The eight surviving conditional offers are unenforced instruction prose, and **whether they actually fire usefully in live work is unmeasured.** Two adversarial rounds (16 findings, then 18 in those fixes) resolved the *structural* question — see DECISIONS.md's 2026-08-18 entry on the observability test, which deleted two offers rather than patching them a third time — but reviewing the text again is explicitly not the next step, since prose with no artifact to inject a defect into cannot be shown capable of failing however many rounds are spent on it. The open item is evidence from use: note whether an offer appears at a moment it helped, and whether one appears where it reads as noise. That is the only signal that can settle this, and it cannot come from another review.

## Rules / Never do
- Read CLAUDE.md, DECISIONS.md, and SESSIONS.md at the start of every session and stay anchored to them (enforced by this repo's own SessionStart hook once added — see `.claude/settings.json`)
- Verify external claims (API behavior, docs, third-party task briefs) against live/actual behavior before trusting them and writing code against them
- Use plan mode (or otherwise get explicit sign-off) before non-trivial implementation work
- Commit only when explicitly asked; never use destructive git operations (force-push, hard reset, history rewrites) without explicit confirmation
- Always read a file before editing it; if an exact-match replacement fails, re-read the file to find the actual current content rather than reaching for a regex fallback
- Update SESSIONS.md and, if status changed, CLAUDE.md as part of the same work — not as a separate cleanup pass remembered later
- If README.md describes a feature, command, or setup step that no longer matches reality, fix the README in the same change — don't leave it to drift
- Don't add a new composable skill without updating this CLAUDE.md's Architecture section in the same change
- Update STACK.md whenever a technology is added, replaced, retired, or reaches a milestone worth recording — and only mark something "in use" once actually verified running, not when first written
- Proactively suggest a checkpoint when EITHER (a) the session has covered several unrelated subtasks or run long, OR (b) the working directory has changed to a genuinely different project than where the session started — (b) is a stronger signal than (a) and shouldn't wait for (a) to also be true. To checkpoint: update SESSIONS.md/memory with current state, then suggest `/clear` before continuing.
- Any change to the secrets-guard regex or `.gitignore` baseline pattern must be re-verified with `tests/run_fixtures.sh`, with new cases added to `tests/fixtures/*.txt` first — never trust a manual spot-check alone for these patterns again.
- The conditional cross-skill offers in each skill's `## Closing out` section are **judgment guidance with no mechanical enforcement** — instruction prose an assistant may or may not follow, with no artifact to inject a defect into and therefore nothing `tests/run_fixtures.sh` can exercise. Never describe them as tested, verified, or validated by a green suite. Before adding another one, apply the observability test: can the skill determine the trigger's truth from its own numbered steps? If not, it does not go in — two adversarial rounds (16 findings, then 18 in those fixes) established that an unobservable trigger reliably degrades into an always-true or never-true one, and that patching it produces a new one rather than converging.
- Re-run the `qc-review` calibration (`tests/calibration/qc-review/`, procedure in its README) after any edit to `skills/qc-review/SKILL.md`'s Steps 2 or 3, when the reviewing subagent's model changes, and before relying on a clean review for a release or handoff — then append the result to `RESULTS.md` whatever it says. This is manual and non-deterministic by construction; it must never be added to `tests/run_fixtures.sh`, and a green fixture suite must never be described as covering it.
- Never add or modify a check in `skills/foundry-audit/audit.sh` without adding its mutation case to `tests/run_fixtures.sh` in the same change — a case that injects a real instance of the defect the check claims to catch and confirms it fires. A green suite proves nothing about a check nobody has watched fail. If a proposed check can't be mutation-tested because it needs semantic judgment rather than pattern matching, it does not go in the script at all; it goes in `SKILL.md` explicitly labeled as judgment, so it can't inherit the tested checks' credibility.
- When writing or editing a conditional safeguard in any SKILL.md ("if X, do Y" prose meant for a future AI session to follow), explicitly write out and consider the negative branch — what happens if X is never true, or if the precondition that would make X checkable doesn't exist yet — before considering the rule done. Eight straight review rounds in this repo (Sessions 12-19, including the mechanism built specifically to fix this pattern) found the exact same failure shape every time: absence of a trigger condition silently treated as "the safe case" instead of "unknown, flag it." This is a structural risk specific to writing multi-branch instructions in natural language for an LLM to execute, not a one-off mistake — assume it'll happen again unless the negative branch is checked explicitly, every time, not just when a review happens to catch it.
- Archived history is deliberately excluded from the SessionStart hook's auto-load, and opening it is opt-in. Don't read an archive speculatively or "for completeness" — that spends the exact context the archive exists to save. Open one only when the current task genuinely needs it: tracing why a decision was later reversed, recovering the original reasoning behind a rule that now looks arbitrary, checking whether an approach was already tried and rejected, or reconstructing what a since-changed requirement used to be. Move old content into an archive **verbatim** (never summarize during a move, so the move itself cannot lose anything) and keep the pointer block above ("Where the history lives") in sync with each archive and the range it covers. That pointer is the only part guaranteed to load every session, so it is the entire mechanism by which the archive stays findable; an archive nothing points to is indistinguishable from a deleted one. When an archive pass becomes *due* is now measured rather than noticed by luck: `bash skills/foundry-audit/audit.sh`'s `auto-load budget` line reports the injected total and which file is largest on every run, INFO once over budget, FAIL at the ceiling. Treat an over-budget INFO as due work, not as advisory — and never clear it by raising the threshold.

## How to run / Bash commands
- Install: `./install.sh`
- Invoke: `/foundry-init` in any project directory (after install), or any individual `/foundry-*` skill standalone
- Test suite: `bash tests/run_fixtures.sh` — re-runnable adversarial fixtures for the `.gitignore` baseline, secrets-guard regex, Hook 4's directory-drift logger, Hook 3's status/offer hook, Hook 5's push-time qc-review offer, the Hook 1/3 SessionStart merge guard, and `foundry-audit`'s mutation cases; runs automatically on every push/PR via `.github/workflows/fixtures.yml`. Beyond this, verification is direct skill invocation against scratch/real projects (see Current Status).
- Doc audit: `bash skills/foundry-audit/audit.sh` — mechanical structural check of this repo's own doc set, including the `auto-load budget` line (size of what the SessionStart hook injects, as a percentage of budget — read it here rather than from a number copied into a doc). Exit 0 clean, 1 findings, 2 harness error. Worth running before any push that touched documentation. Add `--numeric "mutation cases"` when the fixture suite grew — that exact cross-check caught two stale counts (README.md and a DECISIONS.md `Enforced at:` line) the session that added the budget check, neither of which any other check could see.
